# TEXporter for MuseScore: pipeline and API evidence

## Supported MuseScore interface

Checked against the official **v4.7.5** source before implementation, plus QML examples shipped with the installed 4.7.5 application. The [official download page](https://musescore.org/en/download) listed 4.7.5, released September 8, 2026. The installed `MuseScore4.exe --long-version` reported `Version 4.7.5; Build 3654226`.

Current `Cursor::tempo()` returns `score->tempo(fraction()).val`, an effective tempo-map value. It is quarter notes per second. The reader multiplies by 60; it never extracts a number from formatted tempo text, so dotted-note and hidden metronome markings use their actual playback values. Cursor seeking uses exact fractions and **All** segments; it does not require a note on staff 1 at the bar start. The reader traverses actual measures, not `firstMeasureMM`, so displayed multimeasure rests do not collapse the measure count.

The legacy FileIO implementation restricts writes to allowed content paths and returns a success boolean. The UI checks that boolean and reads the output back for a full-string comparison, allowing the one extra terminal newline added by the current FileIO.read() implementation. Before opening the picker, the plugin refreshes a MuseScore `Settings` object and reads `application/paths/myScores` with `value()`; it declares no saved QML properties and does not change preferences. If the preference is absent, the exporter shows an actionable error asking the user to choose Scores in Preferences and retry. It does not import `Qt.labs.platform`: despite files present in the installation, the user's MuseScore extension log confirmed that this module was unavailable to the plugin engine and caused the 1.2.4 dialog to fail loading. `ExportPath.js` converts file URLs and joins the directory with the sanitized filename for `FileDialog.folder`. The default save name is sanitized; the chosen filename must already have the correct extension to preserve native overwrite-confirmation behavior.

## Modules

1. `ScoreReader.js` adapts live MuseScore objects into `{title, measures, events, warnings, attention, navigation, selection}`. Measures retain actual `durationQuarters`, `isPickup`, detected `holds` and `freeTime`. No score mutations, archive parsing, pitch analysis or external processes.
2. `Model.js` validates meters/tempo, rounds quarter BPM to two decimal places without changing the source measures, and groups adjacent measures using the rounded tempo. Each region stores score measure labels, independent chronological indices, unique written `sourceIndices`, start/end ticks, bar count, meter and quarter BPM. Actual-duration/override bars and bars requiring timing decisions occupy isolated regions. Changes to any relevant setting break the region.
3. `TonalEnergy.js` takes regions plus options and the exported-default template. It knows nothing about MuseScore. It validates the regions, synchronizes duplicated TE fields, escapes XML text and emits deterministic XML.
4. `Template.js` contains ordered attribute/child trees generated from a real TE preset/group. Unknown fields and disabled drone/poly/count-in subtrees survive serialization.
5. `TEXporter.qml` handles profile/options, the live editable table, inline timing choices, save picker and results. Text edits refresh validation/serialization immediately; range/structure options schedule a brief debounced rebuild with stable-region edit preservation. The complete runtime includes `lib/`, the scoped control components in `ui/` and logo files in `assets/`.
6. `RepeatOrder.js` expands ordinary repeat barlines into a finite measure-visit sequence before region grouping. It is independent of MuseScore and the TE serializer.
7. `Range.js` validates written-bar bounds, freezes disabled settings at the first selected bar and filters full-score repeat visits. Original `sourceIndex` values retain naming and repeat semantics.
8. `Preview.js` validates table edits without mutating source regions and computes estimated score duration. It adds no count-in presets. `countInEnabled` is the sole count-in preference and defaults to true. `TonalEnergy.js` applies it to the group's native Range Start count-in in 1.3.2.
9. `ExportOptions.js` normalizes reusable settings and handles malformed persisted JSON. A separate MuseScore `Settings` category, `TEExporter`, stores options; it does not write the application Scores preference or score-specific range/name/edit state.
10. `Preflight.js` identifies required timing decisions by written bar position, validates total count lengths, applies decisions to cloned selected measures and collects affected-measure warnings. It deduplicates repeated visits and suppresses grouping warnings once all corresponding exported presets have a valid manual grouping.

## Branding and installation compatibility (1.6.0)

The MuseScore product is **TEXporter**, shortened to **TEX**. Its entry point is `plugin/TEXporter.qml`; new archives follow `dist/TEXporter-<version>.zip` with a single `TEXporter/` top-level folder. `tests/package.ps1` rejects a missing new entry point or a remaining legacy `TEExporter.qml` source file to prevent distributing duplicate plugins. Historical archives are retained locally and excluded from this repository. Logo/prompt documentation is in [LOGO.md](LOGO.md); distribution copies adjust the logo's relative path to the bundled runtime asset.

The internal `TEExporter` Settings category remains unchanged so existing export preferences continue to load. The development installer accepts `-Destination` for the Plugins location shown in MuseScore preferences, creates a full project-local backup and verifies every copied runtime/asset hash. Current updates accept `TEXporter.qml` as the installed entry. For legacy installations, remove only the old `TEExporter.qml` after verifying the new runtime is complete, as described in the README. MuseScore may need the renamed plugin enabled again after restart.

The footer links to the [repository](https://github.com/AgentDelta4/TEXporter), [latest release](https://github.com/AgentDelta4/TEXporter/releases/latest) and [bug issue form](https://github.com/AgentDelta4/TEXporter/issues/new/choose). The GitHub issue form collects version, export settings and reproduction details.

Version 1.4.0 adds `fullMet`, `halfMet`, and `downbeatMet` preferences (defaults true, false, false). `TE.serializeExports()` snapshots the edited regions into one independently labeled group per selected version. The single-group `TE.serialize()` retains its full-click default for existing adapters. `getBeatMasks()` returns exact decimal mask strings and the signed low 32-bit legacy mask, using the click-pattern reference fixture for 4/4 behavior. The native count-in is serialized identically for every version.

The dialog saves these snapshots through a finite queue. Every file gets its own native save picker and overwrite confirmation. `Qt.callLater()` opens the next synchronous picker only after the preceding accepted callback returns. Cancel/error stops the queue and reports already verified saves; duplicate destinations in one queue are rejected before writing. Version selection refreshes output without rebuilding or discarding edited rows.

For a new notation adapter, return the same measure/event model and call `Model.regions()` and `TE.serialize()`. No MuseScore types occur in the latter two modules.

## Live preview and inline handling (1.7.1)

The dialog analyzes the score when opened and updates its preview automatically. Editable text fields use `onTextEdited`, including starting/ending BPM, Bars, meter, ramp offset/length, name and /8 grouping. Those edits refresh validated regions, estimated duration and pending version outputs without waiting for focus loss. Briefly invalid text remains visible with an actionable error; it does not silently reuse older valid output.

Changes to range, split/repeat behavior and other structure options schedule a roughly 150 ms rebuild rather than requiring an Analyze action. Edited fields are restored when region identity remains stable, using written source membership and repeat visit identity. A merge, split or different selected passage may produce new identities; those rows receive newly derived defaults. Raw range text is validated independently of a numeric control's retained value, so invalid text cannot export a stale range after focus loss. Export resolves pending rebuilding before creating the save snapshots.

The `ui/` folder contains scoped `QtQuick.Templates` components for explicit blue checked, selected and focused states. A separate Qt check confirms their colors remain blue under a yellow Windows host palette. Updated Qt smoke tests also verify that counts/grouping edits preserve focused control identity and caret position. Editable preset fields stay specific to a playback visit; hold decisions remain shared by written bar. Count-unit/meter changes retain the chosen physical duration, including /8 conversions.

Only detected hold/free-time rows receive inline handling controls. No separate timing editor, Analyze/reset action or manual hold-declaration action is exposed. Required rows start without a choice; preview remains visible, while export remains blocked until every selected written-bar requirement has a valid **Keep steady clicks** or **Set total counts** decision. Inline decisions share written-bar keys across repeated visits and update preview lengths immediately. Score free-time text remains detected on its containing bar. To review a longer unmarked passage, add appropriate markings to each affected bar in the score.

Closing and reopening the dialog resets score-specific edits and choices. Existing saved general options continue to load from the unchanged `TEExporter` settings category. Export must use the latest validated preview, including pending option changes, before snapshotting the independent files for the save queue.

## Eighth-note grouping (1.4.1)

The current API declares `TimeSig.groups`, but [PropertyValue::toQVariant](https://github.com/musescore/MuseScore/blob/v4.7.5/src/engraving/types/propertyvalue.cpp) explicitly marks `P_TYPE::GROUPS` unsupported, so the exporter never reads that property. It uses [numeratorString, ChordRest.actualBeamMode and Beam.elements](https://github.com/musescore/MuseScore/blob/v4.7.5/src/engraving/api/v1/elements.h), which are readable. Additive numerator text takes precedence. Otherwise a complete grid of straight eighth-note chords establishes beam boundaries, including manual beam starts from beam membership. Incomplete rhythms, un-beamed chords, tuplets, cross-staff beams and conflicting full voices do not establish new grouping. Pitches are not accessed.

Grouping persists through later sparse/rest measures with the same signature and resets at a new signature. A new readable bar can replace it. Unclear /8 bars have no grouping and retain all eighth clicks in Half Met, with an actionable warning. The preview accepts explicit positive group lengths summing to the numerator; these override inference for the exported preset. Grouping is copied through ranges, meter freezing, repeat visits and regions; a different grouping prevents merging. Grouping-only splits remain unnamed under the existing naming rules.

Full Met clicks every eighth and applies accents at grouping starts. Half Met clicks those starts; Downbeat clicks only 1. Straight keeps the same click masks but disables accents. Non-/8 behavior and the native count-in stay unchanged. Both click and accent masks use exact decimal text for all 64 counts, with signed low-32-bit legacy fields. The time signature and quarter BPM remain unchanged, so silencing clicks does not alter bar duration.

## Actual duration and required timing decisions (1.5.0)

Nominal meter describes musical counts; actual `durationQuarters` describes the timeline. `Model.regions()` retains actual lengths on pickup/irregular regions instead of replacing them with nominal full bars. An explicit `durationOverrideQuarters` replaces the whole selected measure's duration. `sourceDurationQuarters` retains the original length for pickup alignment. Such regions keep `barCount=1` and `isDurationSpecific=true`; preview name/BPM/grouping edits preserve them, while Bars/meter edits are rejected.

`TonalEnergy.playbackMeter()` represents the effective length as one exact meter bar, starting with the nominal denominator and refining through /64 only when needed. It never coarsens the audible grid to squeeze in a long duration. A non-dyadic duration, a value shorter than the /64 grid or more than 64 encoded counts blocks export with a measure-specific error. The source region retains nominal meter; only the serialized preset/meter map uses the encoded meter. Preset and meter-map bar count are 1, `bardur=1`, and existing `beatsonly=0` remains. Unknown TE fields and native count-in data are unchanged.

`playbackMasks()` projects nominal clicks/accents into that encoded bar. An opening pickup aligns with the tail of its nominal bar; a short closing/interior bar aligns with count 1. Refined subdivisions add timing positions, not extra audible clicks. A one-quarter 4/4 pickup therefore exports 1/4 with a soft Full click and no Half/Downbeat click. A 3-quarter closing bar exports 3/4 with original counts 1–3. /8 group starts retain their source positions. A chosen duration longer than a nominal bar cycles the original count pattern through the additional time.

The reader collects fermatas, caesuras, breath marks with positive playback pauses, section layout pauses, and recognized free-time text. Staff copies are deduplicated. Native fermata stretch may affect `Cursor.tempo`; the reader recovers musical quarter BPM so a required user choice controls the held length rather than silently baking that stretch into the entire bar's tempo. Playback settings do not provide a conductor's cue duration.

For every selected written bar requiring review, its preset row begins with no handling choice. **Keep steady clicks** retains its notated duration; **Set total counts** validates a whole-measure length in the field's displayed count unit and sets `durationOverrideQuarters`. That unit matches the selected/export meter, including frozen meter settings. Decisions are keyed by written bar position, copied to repeat visits and retained only within the current dialog. Each reviewed bar and its following boundary remain isolated even with steady clicks, keeping preview edits stable when an inline decision changes. Bars/meter are fixed on all required timing rows; name/BPM/grouping edits remain available.

`Range.selectWritten()` freezes ordinary bars to the first selected meter's full length when meter changes are disabled, preserving the prior freeze behavior. Genuine source pickup/irregular lengths and explicit overrides remain exact. `Range.selectVisits()` carries effective duration and timing-decision flags into each playback visit. Regions retain written `sourceIndices` plus `visitNumber`, so attention and edits remain tied to the same musical position despite duplicate printed numbers.

The compact **Needs attention** panel collects selected-measure diagnostics and serializer warnings. With no unresolved choices/errors it stays collapsed; optional warnings remain available to expand. Required choices and invalid values prevent the save queue. An unresolved grouping warning disappears only when every exported region covering that written bar has a valid grouping. No in-bar pause or silent cue preset is inferred.

## Event model and future extensions

Tempo events contain absolute `tick`, `measureIndex`, `offsetTicks`, `quarterBpm` and source text. Meter events contain those positions plus numerator, denominator and staff track. Tempo markings inside a measure continue to take effect at the next measure; exact actual durations do not introduce in-bar tempo presets. Version 1.3 adds ramp events with absolute start/end ticks, initial/target quarter BPM, easing and an ID. Each intersecting measure receives a clipped ramp with quarter-beat offset/length and interpolated endpoints. Fractional-quarter alignment, overlap and an internal explicit tempo marking attach an error to the affected measure; range selection rejects it only when selected. Nonlinear easing warns and uses linear endpoint interpolation.

MuseScore builds the gradual endpoint from its start tempo multiplied by `tempoChangeFactor`; playback-disabled lines are skipped. The exporter uses that endpoint rather than guessing from “accel.” text or a later marking. Full-bar fragments of the same ramp merge only with continuous rounded endpoints, matching meters, and no selected section/repeat boundary. Partial fragments remain separate. `TonalEnergy.js` encodes the observed transition shapes, synchronizing preset and tempo-map fields. See [transition evidence and remaining device checks](ACCELERANDO.md).

Data flow: read the complete score → validate selected written bars → expand ordinary full-score repeats → retain selected visits → build preview regions → apply inline timing choices and live row edits → collect attention/validate export → serialize score presets and native group count-in settings once all required decisions are resolved. Pending choices do not hide the preview or permit a save. Range filtering does not invent a new repeat structure. Count-ins do not change preset order/counts, score bars or the approximate score duration. TonalEnergy handles count-in timing at Range Start. Duration uses the effective actual/chosen length and integrates a linear BPM change over quarter-beat position where applicable; it is labeled approximate.

Written measure labels can restart or skip; merging uses chronological indices, never label arithmetic. Pickup detection compares nominal-meter length with actual duration. Denominator changes are independent of tempo; the exporter preserves quarter-note duration and disables TE's automatic eighth-duration conversion. Playback tempo multipliers, individual hold-note pauses and complete repeat navigation are not reconstructed. The user chooses a fixed total held-measure length; numbered endings and D.S./D.C./coda expansion remain deferred. /16 grouping is unchanged.

## Section splitting (1.1)

The reader adds `hasRehearsalMark`, `doubleBarlineBefore` and `doubleBarlineAfter` to each measure. Rehearsal and double-barline events retain their exact tick positions in the event stream. Barline elements are scanned on every staff's primary track; copies across staves create one boundary. The exposed `BarLineType.DOUBLE` constant is used instead of a hard-coded numeric type. Repeat and final barline types remain distinct.

`Model.regions()` accepts `splitBy: 'settings' | 'rehearsal' | 'double'`. A selected marker prevents merging even when the meter and tempo match. A rehearsal mark splits before its containing measure; an ending double barline splits before the following measure. A double barline at the start of a measure also prevents merging into the preceding region. The score's first measure always begins a region, and an ending barline never produces an empty trailing region. Tempo/meter differences remain mandatory boundaries. The QML dialog combines matching bars within sections and exposes one-preset-per-measure only in settings mode.

## Boundary-based names (1.1.1)

The reader stores plain rehearsal text in rehearsalName after removing MuseScore XML formatting and decoding text entities. Repeated staff copies share the label; different labels in one measure warn and use the first nonempty label. Model.regions assigns boundaryKind when a selected boundary starts a region and derives presetName from that boundary. Rehearsal mode uses the label; double mode uses String(startMeasure), including score numbering offsets. An otherwise unnamed region starting at the first written bar receives Top, regardless of pickup or displayed numbering. Later tempo/meter-only splits receive an empty name. A simultaneous settings change retains the selected boundary name. Version 1.2 appends (repeat) for later measure visits. The serializer writes presetName exactly, XML-escaped, with no numbering, measure-range or tempo suffix. Diagnostic preview and warnings identify unnamed presets by region index and measure range.

## Ordinary repeat playback (1.2)

The supported legacy API exposes `MeasureBase.repeatStart`, `repeatEnd`, `repeatJump` and `Measure.repeatCount` in elements.h. MuseScore's [measure implementation](https://github.com/musescore/MuseScore/blob/v4.7.5/src/engraving/dom/measure.cpp) defaults repeat count to 2; its [repeat engine](https://github.com/musescore/MuseScore/blob/v4.7.5/src/engraving/dom/repeatlist.cpp) treats that count as total plays. Section layout breaks are read from measure elements with `LayoutBreak.SECTION`. The reader also detects `Element.VOLTA` spanners and playback jumps to flag unsupported navigation.

`Cursor.nextMeasure()` traverses written measures, and `utick` maps a tick into the native repeat list; neither provides an iterator over every playback visit through the legacy interface used here. This version therefore uses supported repeat metadata with a separate ordinary-repeat expander, rather than parsing score archives or claiming native playback navigation support.

`RepeatOrder.expand()` prevalidates flat repeat blocks/counts and then creates shallow copies of analyzed measures in visit order. An omitted start anchors the first end repeat to the current score/section beginning. Multiple end repeats reusing that implicit start, nested/unmatched starts, and unsupported endings/jumps fail Follow mode. Ignore mode simply copies written order. The source model is never mutated.

Each visit retains `sourceIndex`, written measure number/ticks, settings and markers, and adds chronological `index`, `visitNumber`, `isRepeat` and `playbackBoundary`. Source double-barline boundaries are carried into repeated visits even when the preceding played measure differs from the preceding written measure. Explicit repeat starts, jumps/exits and repeat-status changes prevent region merging. Model grouping appends exactly one (repeat) suffix from the source label on every later pass, or uses (repeat) alone for an unnamed region. The first written bar retains the Top fallback on later visits, producing Top (repeat); sourceIndex identifies the opening independently of playback order and displayed numbering. Fresh tail measures lose the repeat status. The preview distinguishes written count from played count.

This is ordinary barline expansion, not MuseScore's complete repeat-navigation engine. Voltas, jumps and ambiguous structures cannot silently pass Follow mode. Repeat counts are capped at 1000 and expansion at 100,000 measure visits. Runtime MuseScore and TE validation remains outstanding.
